
## 概述
本次优化是希望通过在原本的代码基础上增加一些限制来加强活动相关数据的控制，减少重复代码。

## 目前存在的问题

- 1、自由度太高，目前的活动数据都是简单缓存一份键值对，其余由单个活动自由发挥。这是最不会出问题的做法，但是这也导致了一些混乱。比如同一个活动类型但是不同界面的活动，他们通常都会自己写一份几乎相同的数据处理逻辑。这会导致很多重复代码，还有如果这个活动类型的数据结构有变更有可能会遗漏掉另一个活动的逻辑修改

- 2、目前取用活动数据和获取活动状态的时候是用活动id做核心的，这就导致了不管是界面，列表组件，所有的东西只要想在里面处理活动相关的东西我都要么在里面重新通过moduletype获取一个活动id，或者想法版传个活动id进去

- 3、缺少明晰的活动数据结构，为后续维护带来困难。当我维护一个很久没碰的活动时我通常都要先开活动，跑起来断点才能查看这个活动的活动数据结构，有很多时候还可能会忘记数据结构里的字段分别代表什么，还要为它去看代码逻辑

- 4、活动数据的取值路径较长，每个取值的代码里都有很长一段重复代码，比如我要获取活动数据里的一个字段，我要先按以下步骤获取
    - 通过moduletype获取到当期正在开启的活动id
    - 再通过id获取到原始的活动数据activeData，但是这个活动数据里通常只有activedata.data 里的东西才是有用的
    - 所以需要取data字段
    - 最后才能拿到我需要的activedata.data.XXX字段
- 再加上以上一长串加上几乎每一步都需要对获取到的东西判空，这些都是重复代码

## 解决方案
综上所述，我提出几个手段尝试解决以上问题
- 1、收束活动相关代码的管理：同一个activeType服务器给的东西可以确定都是相同的，包括数据结构和配置结构，所以要根据每个活动类型建立一个活动数据类，原则上看可以往里面塞这个活动类型相关的全部数据和代码，包括但不限于取值，奖励获取相关逻辑，通过活动数据获取对应配置，活动的红点计算等。结构如下
```typescript
export class ActiveDataBase {
    local _activeState: ActiveState; //活动状态（服务器的原始数据）
    local _activeData: ActiveData; //活动数据（服务器的原始数据）

    local _data: any; //活动的主要内容 具体类型由子类定义
    
    //父类应提供活动开启判断，显示开启判断，剩余时间获取和活动配置获取等函数
}

export class XXXActiveData extend ActiveDataBase {
    local _data: XXXData; //通过这种方式提醒活动开发者增加活动数据

    // 子类应提供本活动类型相关的通用逻辑
}

// 有活动数据下推时根据活动类型生成对应数据对象，因为不确定活动状态和活动数据什么时候下推，任意下推一个就创建，后面那个创建时通过赋值把数据传进对象中

//只有当活动数据和活动状态都被置空后该对象才能删除或者回收进对象池

//数据对象管理用moduleType.id作key，活动数据数组作value的键值对管理

```
- 2、弃用掉活动id，回归moduleType为核心。在moduleType中增加活动数据对象的获取函数，同一个moduleType有多个活动数据时允许自定义数据筛选逻辑。

## 补充
- 以上修改可以做到完全不影响旧有的活动逻辑，两者可以并行，模块开启判断可以沿用旧逻辑。由新活动试行，所以可以不考虑修改对旧活动的风险。只需要考虑以上修改是否真的能更好用。
